The watchdog's session result (`.overnight/logs/session-1.json`) shows the same: `fast_mode_state: "off"`, `usage.speed: "standard"`.

**Result:** fast mode is observable from `-p` output (`fast_mode_state`, `usage.speed`), and it is off for the run. On 2.1.270, headless `-p` sessions keep fast mode off even without the override, because fast mode needs an SDK opt-in. The watchdog's `--settings '{"fastMode": false}'` is therefore harmless but not what keeps fast mode off here; it stays as a guard in case a future version changes the `-p` default. Spec section 11's open item is resolved.

## Plugin-interference observations

1. **context-mode SessionStart hook** injected its `context_window_protection` block into the unattended session, telling it to route work through `ctx_*` MCP tools and to avoid Bash/Read/Write. The main session named it as suspected injection in its first message and ignored it. Two subagents did follow it: the Opus final reviewer made 4 `ctx_execute` calls and the Task 1 implementer made 1 `ctx_batch_execute` call. These were small detours with no effect on the outcome.
2. **claude-mem PreToolUse:Read hook** fired on 34 of 53 Read calls, across the main session and subagents. On files it has "prior observations" for, it cuts the Read to line 1 ("Only line 1 was read to save tokens") and points to its `get_observations` / `smart_outline` tools. The truncation is real, not fabricated as the agents assumed. The main session and at least 4 subagents noticed, re-read with `cat` or used the content they had just written, and carried on. The session logged this as a `needs-human` JOURNAL entry and repeated it in its final result text.
3. **Superpowers' own SessionStart mandate** was called "fake" by the model in the `/goal` environment probe, but in the real run the main session still used `superpowers:brainstorming`, writing-plans, and subagent-driven development, because the project's CLAUDE.md "Unattended run" section tells it to.
4. **Interactive driver session:** a SessionStart hook printed `SessionStart:startup hook error — Hook output looks like a JSON object but is not valid JSON` (another installed plugin's hook, not `overnight`, which has no hooks). It had no effect.
5. No refusals, no permission denials (`permission_denials: []`), and an empty session stderr. The unattended session never stopped to ask a question.

Net: the hooks cost some attention and a few extra tool calls. They did not derail the run or change any commit. For the course run on this machine, expect the same `needs-human` note in the journal.

## Minor observations (not defects)

- The `start` skill asks for "one summary" table before AskUserQuestion. Sonnet put the whole summary (criteria with "as written", approved actions, stop time, model) into the question text and the first option's description instead of printing a separate table. Everything needed to check was visible.
- `status` reports `tmux session: overnight-tally (alive)` after the run is `done`, because the launch command keeps a shell open (`exec "$SHELL"`) after the watchdog exits so the log stays readable. This is by design, but "alive" next to `status: done` can read as still running.
- The session JSON's `duration_ms` (120,446) covers only the last turn; the watchdog's own clock (2026 s) is the reliable duration and is what `state.json` records.
- Only two `goal_status` entries appeared: one when the goal was set (met false, no reason) and the final met verdict. The session never ended a turn short of the goal, so the evaluator never had to push it on. Waits for background subagents stayed inside the session.
- The project's final result text says "15 commits on main"; the repository has 11. JOURNAL entries for the Task 1 and Task 2 reviews were appended after the 08:57 entries, so the journal is not strictly in time order. These are model bookkeeping slips, not plugin behavior.
